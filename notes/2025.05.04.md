Now the next idea I have spearheaded into. I have noticed while testing depthai and rmaptab, that depthai may hang sometimes, so I needed to restart the system. This lead me
to an idea of a generic process health control. Wasn't necessary for a POC, but I just wasn't able to stop. So I did the following:
0. A setup which runs all the pieces of ROS via `supervisord`.
1. A ros node `supervisor_bridge` which connects to supervisord via RPC, gets the list of programs, allow starting, stopping, restarting them. Also publish processes status
into `/diagnostics` which is kind a of generic convention
2. A ros node `watchdog` which subscribes to a certain topic, and restarts a process via `supervisord` if there is no messages for 5-10s.

Spent whole day on that, and got it well tested manually. I still don't know how to write a test for a ROS node. But this bridge might be a valid OSS package idea.

Ok, I did some research, and learned a lot:
1. Rtabmap is not VIO (Visual-intertial Odometry system), its VO with some reliance on IMU (controlled by OdomStrategy)
2. VIO is OpenVINS or VINSFusion or https://github.com/MIT-SPARK/Kimera-VIO. There are pros and cons for all:
    * OpenVINS supports super points, basically feature tracking on OAK D camera VPU which would make odometry much more reliable
    * VINSFusion can do loop closure and fusion with GPS data

I kinda like the idea of using super points, but it seems quite lame that it reqiures kalibrating OAK-D + IMU which a whole unit of work. Here is some example config https://github.com/chobitsfan/VINS-Fusion/tree/oak_d/config/oak_d which I guess I can repurpose, but I it seems too much hassle to be honest.

I guess I am going to stick to this example https://github.com/introlab/rtabmap_ros/blob/ros2/rtabmap_examples/launch/depthai.launch.py: it actually seems to be newer. And I will keep exploring how can I improve rtabmap SLAM.
